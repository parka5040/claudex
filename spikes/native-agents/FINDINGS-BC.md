## B: evidence and caveats

- `claude plugin validate spikes/native-agents/mod-b` passed with one author-metadata warning. To repeat: `bash spikes/native-agents/run-bc.sh b foreground`, `b background`, `b taskstop`, or `b cancel`. The ticker prints at 0, 15, 30, 45, 60, **135**, ..., 225 seconds (`mod-b/hooks/ticker.sh`). The full foreground run exited 0, `is_error:false`, `num_turns:2`, zero API tokens; the original full-run start/finalizer markers differed by **225.012 s** before later probes reused those marker paths (`captures/b-foreground-timing.txt`). Its retained result has `duration_ms:228563` (`captures/b-foreground-output.txt`). The contemporaneous pre-handback API transcript read was user/assistant/user, with one 454-character text block; the persisted, sanitized *completed* transcript in `captures/b-foreground-transcript.txt` has one 454-character assistant text message and a later second assistant `SubagentHandback` tool-use message.
- Two engine requirements were surprising. The generated Agent schema states background is the **default**; the foreground call must explicitly set `run_in_background:false`. A `turn.step` generator must **return a complete `TurnStepResult`**, not merely yield chunks: the first attempt logged `turn.step hook skipped: returned the wrong shape (no result)` and let the real model answer. These invalid first attempts are *not* evidence of successful deterministic dispatch. Validated final runs had zero real model usage (`total_cost_usd:0`).
- A plain subagent `end_turn` does **not** finish this build's delegated agent. The engine adds `[handback-send-enforce]` asking for `SubagentHandback`; without it, the subagent loops. The mod streams text and `stop:end_turn` in its first step, then synthesizes `SubagentHandback({message:fullText})` in its next step. The preserved parent result `captures/b-foreground-parent.txt` has `handbackReport.text` with all 454 characters and a leading tool-result reminder saying the report was delivered as a message, not repeated as plain leading text. The main API transcript observed during the full run included the indented handback text inside its Agent result; later test runs reused `b-main-transcript.txt`. Foreground result reports `<usage>subagent_tokens: 0; tool_uses: 1; duration_ms: 226792</usage>`; background `captures/b-background-events.txt` records `task_notification status:completed` and the same handback summary (report not repeated in the notification itself). The interactive agent-list row at t=15 displayed `↑ 8` as an estimate despite zero billed usage; at t=75 the transcript said `Agent ... finished · 1m 4s`, with no billed token total shown there.
- `captures/b-taskstop-events.txt` records a made-up `TaskStop({task_id: ...})`, `task_notification status:stopped`, and agent status `killed`. `captures/b-taskstop-ps.txt`: same agent id on start/finally; 30.016 s until finalizer; ticker pid 28913 absent (`ps` exited 1). For the **separate SIGINT** experiment, `captures/b-cancel-status.txt` says `nested_exit=0`, ticker pid 27090 gone, `finally=NO`: do not depend on async `$` writes in a finalizer during whole-session shutdown. The first invalid-hook run did write a marker on SIGINT; the corrected run did not, so the latter is the relevant counterexample.
- `plugin/bin/claudex-worker:381` launches `claude -p --output-format json`. The private per-job directory (`:566-586`) starts with `brief`, `meta.json`, lock/child bookkeeping; running stdout is hidden in `.raw.<pid>` and `.out.*`, with final `out`, `err`, `session`, `rc` (`:841-880`); `jobs --json` exposes `state`, `elapsed_s`, `rc`, session only when available (`:907-943`). It has no public tailable per-tool-call stream today. A tiny proxied run in `captures/b-stream-tool.txt` emitted `system.init`, `assistant`/`Bash` `tool_use`, `user`/`tool_result`, `assistant`/`DONE`, `result`/success. Another text-only run is `captures/b-stream-json.txt`. Switching flags **alone** would break the worker's single-document `jq '.result'` parser (`:496-513`); parse NDJSON result events and publish sanitized progress. `--include-partial-messages` would additionally expose token-level deltas; `--verbose` without that flag still yields per-tool-call events.

## U2: interactive limitation

`bash spikes/native-agents/run-bc.sh ui-b` uses a 200x50 PTY and `/tmp/claudex-spike-b-venv` with `pyte`; it sends a real prompt and records rendered frames every 15 s. The working trial used normal permission mode, avoiding an earlier bypass-permission consent dialog; its interactive Agent was **backgrounded even though the synthesized input specified `run_in_background:false`**. `captures/b-01.txt` (t=15) shows a running Agent row without synthetic progress. The driver opened detailed transcript using Ctrl+O at t=20; `b-02.txt` (t=30), `b-03.txt` (t=45) and `b-04.txt` (t=60) showed only the agent prompt and "Waiting for 1 background agent to finish", **not** any of the stdout lines already produced. `b-05.txt` (t=75) showed the complete five-line progress report plus `SPIKEB-DONE` in one "Message from spikeb:shell" after completion; `b-06.txt` (t=82) retained it. `captures/b-ui-metadata.txt` records the actions/times. Thus the observed parent UI/detailed transcript **does not show streamed progress live**; it appears on handback after the step. Earlier first-run/trust dialogs did block trials (`captures/b-trust-121.txt`), but not this successful interactive test. The dedicated agent-management panel was not opened, so its independent live rendering is **UNVERIFIED**. No rollout-disabled message (`hooks modules are turned off in this process`) was observed.

## C: evidence and selection rule

- `bash spikes/native-agents/run-bc.sh c` sent honest `originator: claude-code`, `User-Agent: claudex/0.1 (Claude Code; third-party harness)`, `store:false`, `stream:true`, `reasoning.effort:low` requests through `curl --config -` (auth headers from a shell builtin only). See `captures/b-c-summary.txt`; **each slug was probed once**. Model-list route returned HTTP 200 and object key `models` (10 records). The installed Codex CLI's `~/.codex/models_cache.json` holds matching `models` plus `client_version`, `etag`, `fetched_at`, `identity` (do not print identity); listed records have `slug`, `display_name`, `priority`, `visibility`, `supported_in_api` and other capability fields. First three ranked entries: `gpt-6.1-sol` priority 1, `gpt-6-astra` priority 2, `gpt-6-sol` priority 3. There is **no release-date field** for the model rows.
- Codex responses: Sol HTTP **200**, `response.output_text.done: "hello"`; Luna and Astra HTTP **400**, `The 'gpt-6.1-<tier>' model is not supported when using Codex with a ChatGPT account.` Presence/absence in the model list matched these probes but does not formally guarantee every slug continues to serve.
- A runtime "newest sol" lookup could filter `visibility === 'list' && supported_in_api === true` and anchored versioned slugs `^gpt-(\d+(?:\.\d+)?)-sol$`, then compare parsed versions and/or the lowest numeric `priority`. `priority` is rank, not a release timestamp; `upgrade.model` can hint a successor on retiring rows, but may be absent. Refresh the endpoint/cache and handle no match or backend 400 rather than silently guessing a new slug.
